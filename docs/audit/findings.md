# Audit findings

Report-only. Nothing here has been fixed yet. Each finding: severity, file:line,
what's wrong, a concrete failure scenario, and a proposed fix.

Severity: **high** (security/privacy hole, data loss, crash), **medium** (wrong
behaviour a user will hit), **low** (edge case, robustness, missing test).

## Area 2: Auth flow

Note: the auth gate is not in `src/app/_layout.tsx` (that only loads fonts); it lives in
`src/app/(tabs)/_layout.tsx`, so that file was audited as the gate.

- **[medium] Opening the app offline after the access token expired sends a signed-in user to the login screen**: `src/app/(tabs)/_layout.tsx:24-30`
  `getSession()` refreshes the token when it has expired (Supabase access tokens last 1 hour). Offline, that refresh fails with a retryable network error, and auth-js returns `{ session: null, error }` while keeping the session in storage (`node_modules/@supabase/auth-js/dist/main/GoTrueClient.js:2547-2573`). The layout treats any error as "no session": it sets `loading=false` with `session` still null and renders `<Redirect href="/login" />`. That unmounts the layout, so the `onAuthStateChange` listener that would have caught a later `TOKEN_REFRESHED` is gone too.
  Failure scenario: user uses the app at noon, opens it at 3pm in a basement prayer room with no signal → login screen, even though their session is still valid. They can't sign in offline, and once the connection comes back they still have to do the whole email code flow again (and use up an OTP send).
  Proposed fix: in `checkSession`, when `error` is a network error (`isNetworkError` from `src/lib/errors.ts`), set a `sessionFailed` flag and show `LoadFailedScreen` ("Couldn't connect", Retry) instead of redirecting. Only redirect to login when there is no error and no session. Add a test once the gate decision is pulled out into a pure function (see the last finding).

- **[low] Sign Out does nothing, with no message, when the token can't be refreshed**: `src/components/SideMenu.tsx:28-35`
  `signOut()` first loads the session. If the access token has expired and the refresh fails (offline, server down), auth-js returns that error right away and does not remove the local session (`GoTrueClient.js:3433-3436`). `handleSignOut` only `console.log`s the error, and nothing navigates because `onAuthStateChange` never fires.
  Failure scenario: offline phone, app resumed after more than an hour, user taps Sign Out → the menu stays open, they stay signed in, and nothing on screen tells them why.
  Proposed fix: on error, show a message ("Couldn't sign out. Check your connection and try again.") through the same status overlay the other actions use, and close the menu. Product question for you: the menu uses the default `scope: "global"` (signs out every device), while `src/app/profile.tsx:73` uses `scope: "local"`. Pick one on purpose. I'd recommend `local`, since signing out of one phone shouldn't sign you out of another.

- **[low] Slow profile check shows a blank white screen with no spinner or timeout**: `src/app/(tabs)/_layout.tsx:70-72`
  While `loading` is true the layout returns `null`. `getSession` and the `profiles` select have no timeout, and fetch in React Native has none by default.
  Failure scenario: weak campus Wi-Fi where requests hang for 20+ seconds → the user sees an empty white screen on launch and assumes the app has frozen.
  Proposed fix: render a centred `ActivityIndicator` on `colors.paper` instead of `null`. Optionally race the profile query against a ~10s timeout that sets `profileFailed` so the Retry screen appears.

- **[low] A missing env var crashes the app at launch with an unclear error**: `src/lib/supabase.ts:7-8`
  The `!` assertions only quiet TypeScript. If `EXPO_PUBLIC_SUPABASE_URL`/`EXPO_PUBLIC_SUPABASE_KEY` aren't set at build time (`.env.local` is gitignored, so a cloud/EAS build won't see it unless the variables are set there), `createClient` throws "supabaseUrl is required" when the module is imported, and every screen crashes.
  Failure scenario: first EAS/TestFlight build without the env vars configured → the app crashes on open.
  Proposed fix: check both values and throw a clear error (`"Missing EXPO_PUBLIC_SUPABASE_URL — set it in .env.local or the EAS environment"`), and add the variables to the EAS environment when the build is set up.

- **[low] The auth/profile gate logic has no tests**: `src/app/(tabs)/_layout.tsx:70-83`
  The choice between nothing / login / retry screen / setup / tabs has already had one real bug (the comment at lines 17-19: a failed check used to send existing users to setup), and it would get another branch from the first finding. Right now it's all inline JSX that can't be tested.
  Proposed fix: pull it into a pure function, e.g. `gateFor({ loading, session, sessionFailed, profileFailed, hasProfile }) → "wait" | "login" | "retry" | "setup" | "tabs"` in `src/lib/`, with Jest cases for each branch, including "network error with a stored session → retry, not login".

Checked and fine: the login cooldown uses timestamps, so it stays correct after the app is backgrounded; Verify and Resend always use the locked `sentTo` address; double taps are blocked by `sending`/`verifying`; the interval is cleared on unmount and when the cooldown ends; `authErrors.ts` never shows Supabase's raw messages and has tests for each branch; the `onAuthStateChange` subscription is unsubscribed on unmount.

## Area 3: Profile, setup, delete account

- **[medium] Setup shows "Error code: undefined" when the save fails offline, and has no saving state**: `src/app/setup.tsx:30-57`
  `handleSave` has no `isOffline()` check and no `isNetworkError` branch, unlike every other write in the app. A failed fetch has no `code`, so it falls into the `else` and shows `Something went wrong please try again. Error code: undefined`. There is also no `saving` flag: the Save button stays enabled while the insert is in flight.
  Failure scenario: a new user taps Save on weak Wi-Fi. Nothing visibly happens for several seconds, so they tap again two or three times. If the requests then fail, they see "Error code: undefined", which tells them nothing. If they succeed, the first insert works and the rest hit `23505`, and each one calls `router.replace("/")` again. Also, if `getSession()` returns no session (token expired while offline, see Area 2), `userID` is `undefined`, the insert is refused, and the user sees "Error code: 42501".
  Proposed fix: add a `saving` state that disables Save and shows a spinner, check `isOffline()` first, and map errors the same way `profile.tsx:67` does: network → "No connection. Check your internet and try again.", `23514` → the name message, anything else → "Something went wrong. Try again." with no raw code. If there's no session, send the user to `/login`.

- **[low] Profile spins forever when there's no session**: `src/app/profile.tsx:30-32`
  If `getSession()` returns no user, `load` returns without setting `failed`, so `profile` stays `null` and the spinner never stops. The `error` from `getSession` is also ignored.
  Failure scenario: the app is resumed offline after more than an hour, so the token refresh fails (`{ session: null, error }`), and the user opens Profile from the side menu → endless spinner, no message.
  Proposed fix: `if (!user) { setFailed(true); return; }`. That shows the existing "Couldn't load your profile" message.

- **[low] After Delete account, two things navigate to login at the same moment**: `src/app/profile.tsx:73-76`
  `signOut()` fires `SIGNED_OUT`, so the tabs layout (still mounted under the Profile screen) re-renders `<Redirect href="/login" />` (`src/app/(tabs)/_layout.tsx:62,73-74`). Then this screen also calls `router.dismissAll()` and `router.replace("/login")`. Sign Out in the side menu relies on the layout's redirect alone (`src/components/SideMenu.tsx:34`).
  Failure scenario: depending on the order these run in, the user can see a flicker or get two login screens on the stack, so swiping back from login lands on a second login. I couldn't prove which happens without a device run, so test it on your phone.
  Proposed fix: choose one way to navigate. Either drop the `dismissAll`/`replace` and let the layout redirect, as Sign Out does, or keep them and make the layout skip its redirect while a deletion is in progress. The first is simpler. It needs a quick phone test to confirm the Profile screen also closes.

- **[low] The comment says `scope: "local"` doesn't contact the server, but it does**: `src/app/profile.tsx:71-72`
  auth-js `_signOut` still calls the server's logout endpoint with the access token for `scope: "local"`. It ignores 401/403/404 responses and removes the local session even when that call fails (`node_modules/@supabase/auth-js/dist/main/GoTrueClient.js:3436-3455`). The code is right; only the reason given in the comment is wrong. That matters because you'll be learning from these comments.
  Failure scenario: none at runtime. You'd learn the wrong thing from the comment, and could repeat it in an interview.
  Proposed fix: change the comment to: "Clears the login on this phone. The server call it makes may fail now that the user is gone; signOut ignores that and still clears it."

- **[low] The name rule exists twice, and neither copy has tests**: `src/app/setup.tsx:24-28` and `supabase/profile.sql:26-29`
  The client regex and the database constraint have to stay identical. If they drift, either the client allows names the database rejects (the user gets the vague `23514` message) or the reverse. `validateName` lives inside the component, so Jest can't reach it.
  Failure scenario: someone later widens the client regex (for example to allow "José") but not the SQL → that user gets "Please check your name and try again" no matter what they type.
  Proposed fix: move `validateName` to `src/lib/name.ts` with Jest cases: "Al", "Abdul-Rahman", "O'Neil", "O’Neil", "Mary Ann" pass; "A", 21 letters, "Al  Amin" (double space), "-Ali", "Ali-", "Ali3" fail. Leave a comment next to the SQL constraint pointing to it. Product question for you: names with accented letters (é, ü, ç) are rejected today. Since they come up on a diverse campus, I'd recommend allowing them, but that's a security-tier change to the constraint.

Checked and fine: `delete_my_account()` takes no arguments, deletes only `auth.uid()`, uses `security definer` with `search_path = ''`, and has execute revoked from `public`/`anon`. Its test proves the anon refusal and every cascade path, including that other users' rows survive. The function body in the test matches `delete_account.sql`. Cascaded deletes fire the realtime ping triggers (`live_updates.sql:62-68`), so other users' screens update. `congregation_tally` has no link to users, so ADR 0001 holds. The profile load uses `.eq("id", user.id)` on top of RLS. Delete checks for offline first, has a confirm dialog, and is blocked against double taps by `deleting`. Setup's `23505` → go home handles a profile that already exists.

## Area 4: Security SQL (profiles)

- **[low] The `grant` lines may not limit anything, and other files' comments depend on them doing so**: `supabase/profile.sql:9`
  `grant insert, select on profiles to authenticated` adds privileges but never takes any away. On Supabase projects that have the usual default privileges (`alter default privileges in schema public grant all on tables to anon, authenticated, service_role`), a table created in the SQL editor already has every privilege for `anon` and `authenticated`, including `update` and `delete`. For profiles, RLS still blocks those: there is no update or delete policy, and the select/insert policies are `to authenticated` only. So nothing leaks today. But comments elsewhere say the protection comes from the grant: `src/app/profile.tsx:17` and `supabase/live_updates.sql:73` say "profiles has no update grant", and gender separation in `requests.sql:19,30`, `joins.sql:22,42`, `rooms.sql:20` and `live_updates.sql:83` all depend on gender never changing. Neither the repo nor any test checks what the live database actually has. The same question matters much more in Area 5, because `requests.sql:12` uses a column grant to hide `requester`, and a column grant does nothing if a table-wide `select` is already there.
  Failure scenario: someone later adds a broad update policy (for example "users update their own first_name") thinking the missing update grant still protects `gender` → any user can switch their own gender with one PostgREST `PATCH` and start seeing the other gender's requests and live pings.
  Proposed fix: start the file with `revoke all on profiles from anon, authenticated;` and then the existing grant, so the file says exactly what the database has. Add a SQL test asserting `has_table_privilege('authenticated','public.profiles','UPDATE')` and `'DELETE'` are false, and `has_table_privilege('anon','public.profiles','SELECT')` is false. Run `select grantee, privilege_type from information_schema.role_table_grants where table_name = 'profiles';` on the live project first to see what's there now. This is a grants change, so it's security tier.

- **[low] No tests for the profiles RLS rules**: `supabase/profile.sql:11-21`
  `supabase/tests/` has tests for delete, expiry and live updates, but nothing proves the profiles rules, which every gender check depends on. CLAUDE.md asks for tests on every security rule, including the negative case.
  Failure scenario: a policy is changed or dropped while editing in the dashboard (for example `using (true)` to debug something) → every user's name and gender becomes readable by every other user, and nothing catches it.
  Proposed fix: add `supabase/tests/profile_checks.sql` in the same style as the others, with two fake users (one Men, one Women). As user A: selecting B's row returns 0 rows; inserting a row with B's id is refused; `update profiles set gender = ...` on A's own row changes 0 rows or is refused; `delete` on A's own row changes 0 rows or is refused. As `anon`: selecting from profiles returns 0 rows or is refused. Also check that `'A'`, `'Ali3'` and `'Al  Amin'` break `first_name_valid`.

- **[low] A user can change their account email to a non-OSU address after signing up**: `supabase/verify_osu_email.sql:2-20`
  The hook is a "Before User Created" hook, so it only runs when an account is created. `supabase.auth.updateUser({ email })` changes the email of an existing account and doesn't call it. The app has no screen for this, but anyone signed in can call the Auth API with their own token.
  Failure scenario: an OSU student signs up, then calls `updateUser({ email: "me@gmail.com" })` and confirms the change → the account now signs in with a Gmail address. They keep access after leaving OSU, or can give the account to someone who never had an OSU email. That gets around the "OSU students only" rule the README promises (`README.md:19`).
  Proposed fix: add a `before update of email on auth.users` trigger that raises an exception if the new email doesn't end in `@osu.edu`, using the same check as the hook. Test it with a fake user. If Auth's email change can't be blocked cleanly this way, at least write it down as an accepted limitation next to the one in `delete_account.sql:13-15`. This is security tier.

- **[low] The OSU email hook has no `search_path` and no tests**: `supabase/verify_osu_email.sql:2-4`
  It isn't `security definer` and only uses built-in functions (`lower`, `jsonb_build_object`), which Postgres always looks up in `pg_catalog` first, so there's no real way to hijack it today. Supabase's database linter will still flag it as `function_search_path_mutable`, and every other function in the repo sets `search_path = ''`. Nothing tests the actual check either. The app-side copy (`isOsuEmail`) has Jest cases, but the server copy is the one that enforces the rule.
  Failure scenario: someone later "fixes" the match (for example to allow `buckeyemail.osu.edu`) and writes `like '%osu.edu'` → `someone@notosu.edu` can sign up, and no test catches it.
  Proposed fix: add `set search_path = ''` to the function. Add a short SQL test that calls `public.verify_osu_email(...)` directly and checks the result: `{}` for `a.1@osu.edu` and `A.1@OSU.EDU`; an `error` object for `x@notosu.edu`, `x@osu.edu.evil.com`, `x@gmail.com` and a missing email (`'{"user":{}}'`).

Checked and fine: profiles RLS limits select and insert to `id = auth.uid()`, and the primary key allows only one profile per user. The `gender` check allows only `'Men'`/`'Women'`, which matches `setup.tsx`. `on delete cascade` from `auth.users` matches `delete_account.sql`. The `first_name_valid` constraint matches the client regex in `setup.tsx` today (the duplication is already reported in Area 3). The RLS subqueries in other tables (`select gender from profiles where id = auth.uid()`) run as the caller and can read the caller's own row, so they work. If the caller has no profile, the subquery returns null and `gender = null` matches nothing, so a user with no profile sees no requests, rooms or pings, which is the safe result. `verify_osu_email`: `lower()` handles upper-case addresses, a null email is refused (`null like ...` isn't true), the `%@osu.edu` pattern doesn't match `notosu.edu` or `osu.edu.evil.com`, and execute is revoked from `public`, `anon` and `authenticated` and granted only to `supabase_auth_admin`. The "anyone can delete and sign up again with another gender" path is already written down as an accepted limitation in `delete_account.sql:13-15`.

## Area 5: Security SQL (requests)

- **[medium] The column grant that hides `requester` does nothing if `authenticated` already has table-wide select**: `supabase/requests.sql:12`
  In Postgres, a table-level `SELECT` covers every column, and a column grant only adds to it. Supabase projects normally have default privileges that give `anon` and `authenticated` all privileges on every new table in `public` (see the Area 4 grants finding). The file never runs `revoke all on requests from anon, authenticated`, so unless that was done by hand, `requester` is readable. The comments at `src/hooks/useRequests.ts:37` and `:135` say `select("*")` fails, which suggests the live database may be correct, but nothing in the repo makes sure of it or tests it.
  Failure scenario: if the table grant is there, any signed-in user can call `GET /rest/v1/requests?select=id,room_id,start_time,requester` and get the user id of every same-gender requester. A user id is a stable pseudonym. Someone polling every minute can see "user X posted at Thompson at 1:40pm on Monday, Wednesday and Friday", and anyone who learns X once (seeing who walks in, for example) can follow that person's prayer times and rooms from then on. That's exactly what `my_request_id()` was written to avoid, and it goes against the spirit of ADR 0001.
  Proposed fix: first run `select has_table_privilege('authenticated','public.requests','SELECT'), has_column_privilege('authenticated','public.requests','requester','SELECT');` on the live project. Both should be false. Then start the file's grants with `revoke all on requests from anon, authenticated;` so the file matches the database, and add that check to the SQL test below. This is a grants change, so it's security tier.

- **[low] No tests for the requests and joiners policies**: `supabase/requests.sql:15-36`, `supabase/joins.sql:10-30`
  `supabase/tests/` inserts requests and joiners only as `postgres`, which skips RLS, to set up other tests. Nothing proves the insert, select or delete rules hold, including the gender-separation negative cases CLAUDE.md asks for.
  Failure scenario: a policy is changed while debugging in the dashboard (for example the room-gender clause on `requests.sql:22` is dropped) → men can post into the women's room, and no test catches it.
  Proposed fix: add `supabase/tests/requests_checks.sql` in the style of `live_updates_checks.sql`, using a Men user M1/M2, a Women user W1, and the existing Men/Women/shared rooms. As M1: a request in the Women's room is refused; a request with `gender = 'Women'` is refused; a request with `requester` = M2 is refused; start times of now+2 min and now+50 min are refused; a second request is refused (unique). As W1: `select` returns 0 of M1's rows, a join on M1's request is refused, `request_count()` returns no row for it, and deleting M1's request removes 0 rows. As M2: joining M1's request works; joining when start_time is 3 minutes ago is refused; posting while joined is refused; joining while holding a request is refused; `select member from joiners` returns only M2's row. As anon: `select` from requests and joiners returns 0 rows or is refused, and calling `my_request_id()`/`request_count()`/`check_for_member_request()` is refused. Also the `requester` privilege check from the finding above.

- **[low] The SQL files can't be run in order to rebuild the database**: `supabase/requests.sql:23`
  The requests insert policy calls `public.check_for_member_request()`, which is created in `joins.sql:52`. But `joins.sql` needs the `requests` table (the foreign key on line 4). Running `requests.sql` first fails at `create policy` with "function public.check_for_member_request() does not exist"; running `joins.sql` first fails on the missing table. The live database only works because things were created in pieces by hand. The README setup (`README.md:63`) mentions only `verify_osu_email.sql`, so it doesn't say how to set up the tables at all.
  Failure scenario: you make a fresh Supabase project (a staging copy, a new developer, or recovering from a mistake) and paste the files in → errors part way through, and if you skip the failing policy to get past it, the "can't post while joined" rule is quietly missing.
  Proposed fix: move the `requests` insert policy to the end of `joins.sql` (or into its own file), with a comment saying why, and add to the README the order to run the files: rooms, profile, requests, joins, tally, expiry, live_updates, delete_account, verify_osu_email.

- **[low] A user can be a requester and a joiner at the same time by doing both at once**: `supabase/requests.sql:23`, `supabase/joins.sql:21`
  "Post" checks that the user has no joiners row, and "join" checks that they have no request. Each check only sees data that's already committed. If both inserts run at the same moment (two phones signed in to the same account, or a script), both checks pass and both rows are saved. The unique constraint on `requester` and the primary key on `member` don't stop this, because they're in different tables.
  Failure scenario: user taps Join on phone A and Post on phone B within the same fraction of a second → they hold their own request and are joined to someone else's. The GLOSSARY rule "at most one request at a time" (`GLOSSARY.md:14`) is broken, and if both requests get joiners, `expire_requests()` counts the same person in two congregations. Unlikely in normal use, so low.
  Proposed fix: add a `before insert` trigger on both tables that calls `perform pg_advisory_xact_lock(hashtext(new.requester::text))` (or `new.member`) and then checks the other table again, raising an exception if it finds a row. The lock makes the second insert wait until the first commits, and the second check then sees it. Add the concurrent case to the tests as a comment if it can't be scripted. Security tier.

- **[low] A phone clock that's more than a minute off makes posting fail with a vague error**: `supabase/requests.sql:20`, `src/hooks/useRequests.ts:94`
  The app works out `start_time` from the phone's clock (`Date.now() + minutes`), and the policy checks it against the server's `now()` with only 1 minute of slack. Phones are usually synced, but some people set the time by hand or turn automatic time off.
  Failure scenario: a phone running 2 minutes slow posts "in 5 minutes" → the start time is 3 minutes from the server's now, outside `4..46`, and the insert is refused with an RLS error (`42501`), so the user sees a generic failure and can't post 5-minute requests at all. A phone running 2 minutes fast can't post 45-minute ones.
  Proposed fix: have the server set the time. Add an RPC `post_request(room_id uuid, minutes int)` that is *not* `security definer` (so the existing insert policy still applies), checks `minutes` is one of the `START_OFFSETS`, and inserts with `start_time = now() + minutes * interval '1 minute'`. The app calls it instead of inserting directly. Security tier, because it changes how the insert path works.

Checked and fine: the requests select policy shows only rows where `gender` matches the caller's profile, so requests in shared rooms are still split by gender (matches `GLOSSARY.md:44`). The insert policy checks gender against the profile and the room, and the rooms subquery runs under the caller's RLS, so the other gender's room returns null and is refused. `requester = auth.uid()` blocks posting as someone else. There's no update grant or policy, and RLS also blocks updates if a default grant exists. Delete is limited to your own request or join. The joiners select policy returns only your own row, so no one can see who joined. The joiners insert policy checks gender through the request (a request you can't see returns null and is refused) and has the 2-minute join cutoff, which matches `JOIN_GRACE_MINUTES` in `src/lib/requestTime.ts:6`. The `member` primary key and the `requester` unique constraint allow one join and one request per user. `request_count()`, `my_request_id()` and `check_for_member_request()` are `security definer` with `search_path = ''`, use only `auth.uid()` (no arguments that could be used to look up someone else), are filtered to the caller's gender or own rows, and have execute revoked from `anon`/`public`. A user with no profile sees no requests and can't post or join, since every gender comparison with null fails. Every policy is `to authenticated`, so `anon` matches none.

## Area 6: Security SQL (expiry, tally, live updates, rooms)

- **[low] The comment says the insert and the delete "pick exactly the same requests", but Postgres doesn't guarantee that**: `supabase/expiry.sql:14-15`
  `now()` is fixed for the transaction, but under Postgres's default isolation (READ COMMITTED) each statement takes its own snapshot of the data. A change committed between the `insert into congregation_tally` and the `delete` is seen by the delete but not by the insert. Today the other policies make this nearly harmless: no one can insert a request with a start time 10+ minutes in the past, and the 2-minute join cutoff stops new joiners on old requests. What can still happen is a joiner leaving, a requester cancelling, or `delete_my_account()` running in that gap of a few milliseconds.
  Failure scenario: a joiner taps Leave exactly as the minute's cron run starts → the insert counts them, then their row is gone before the delete, so the tally is one person high, and a request cancelled in that gap gets counted, which ADR 0001 says never happens ("Cancelled requests are never counted"). It's very rare and the error is at most one count, so the real problem is the comment, which you'll learn from.
  Proposed fix: at the start of the function, lock the rows: `perform 1 from public.requests where start_time <= now() - interval '10 minutes' for update;`. A cancel or leave that arrives after that waits until the run finishes. Then the comment is true. Change the comment to say that the lock is what keeps the two statements in step, not `now()`. This is a `security definer`-adjacent function change, so security tier (small).

- **[low] The expiry test fails if it's run in the first 11 minutes after midnight (Eastern)**: `supabase/tests/expiry_checks.sql:22,29-30,52,56`
  Request A starts `now() - 11 minutes`, so between 00:00 and 00:11 ET it belongs to yesterday's tally row. Checks 5 and 6 only look at today's row (`(now() at time zone 'America/New_York')::date`), so they see +0.
  Failure scenario: you run the test at 12:05am → checks 5 and 6 say FAIL even though `expire_requests()` is correct. You might then "fix" working code.
  Proposed fix: compare against A's own day instead of today: use `((now() - interval '11 minutes') at time zone 'America/New_York')::date` in `base` and in checks 5 and 6. Worth also adding a case that proves the day comes from the start time, for example a request that started at 11:55pm ET the day before goes into that day's row.

- **[low] No tests for who can read or write `congregation_tally` or `rooms`**: `supabase/tally.sql:9`, `supabase/rooms.sql:14-21`
  `congregation_tally` has RLS on and no policies, so no one but `postgres`/`service_role` can read or write it. That's right, but it only works because no one ever adds a policy, and the file doesn't say that's on purpose. `rooms` hides the other gender's single-gender room. Neither rule is tested, and CLAUDE.md asks for a negative test on every security rule. `expire_requests()` having execute revoked isn't tested either.
  Failure scenario: someone adds `create policy ... on congregation_tally for select using (true)` to build a "busy rooms" screen, not knowing default grants give `anon` select too → anyone on the internet can read the tally (still anonymous, but not something anyone decided on). Or the rooms policy loses its gender clause → men see the women's basement room at 18th Ave on the map and can post there if the requests policy has also changed.
  Proposed fix: add a comment to `tally.sql` ("No policies on purpose: only the expiry job writes, and only the admin reads. See docs/adr/0001"), and add `supabase/tests/rooms_tally_checks.sql`. As a Men user: sees `050` and the shared rooms, gets 0 rows for `060`. As a Women user: the reverse. As a user with no profile: only shared rooms. ## Area 12: Privacy policy vs reality

- **[medium] Deleting an account leaves the email in Supabase's auth audit log inside your own database, with no time limit**: `docs/privacy-policy.md:15,38`

  Failure scenario: a student deletes their account and later emails you asking whether you still have their email.
